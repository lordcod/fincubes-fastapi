# Дополнение справочника локаций

## Правила импорта

- Дополнительный источник содержит 324 записи и 327 aliases.
- Значения `id`, `city_id` и `region_id` из дополнительного источника не
  импортируются.
- Для уже известных сущностей сохраняются ID исходного справочника.
- Для новых клубов, городов и регионов ID создаются тем же детерминированным
  UUID5-алгоритмом, который уже используется backend.
- `location_candidates` нужны только для подготовки данных и в
  `location_objects` не сохраняются.
- `Озерск` нормализуется в `Озёрск`.
- Для `МБУ ДО СШ Олимпийского резерва` используется Бузулук,
  Оренбургская область.

После согласования справочник содержит 508 объектов, 764 уникальных alias и
772 связи alias с объектом. Количество связей больше количества уникальных
alias, потому что некоторые названия относятся к нескольким регионам.

## Неоднозначные aliases

Отдельные объекты создаются для:

- `ГБУ ДО СО "СШОР ПО ВОДНЫМ ВИДАМ СПОРТА"` — Саратовская область и
  Краснодарский край;
- `СШ` — Кемеровская область — Кузбасс, Красноярский край и Республика Крым;
- `СШ ВВС` — Пермский край и Республика Крым;
- `СШ Дельфин` — Свердловская область и Краснодарский край;
- `СШОР` — Кемеровская область — Кузбасс и Воронежская область;
- `СШОР по ВВС` — Саратовская область и Московская область;
- `СШОР ЦВВС` — Новосибирская область и Кемеровская область — Кузбасс.

У каждого такого объекта `required` равен `["region"]`.

## Изменение API

Полный changelog контракта для обработчиков:
[LOCATION_ALIASES_HANDLER_CHANGELOG.md](LOCATION_ALIASES_HANDLER_CHANGELOG.md).

`GET /admin/locations/aliases/` всегда возвращает массив объектов для каждого
alias, даже если объект только один:

```json
{
  "КВВС \"Касатка\"": [
    {
      "id": "tomsk-location-id",
      "city": "Томск",
      "region": "Томская область",
      "required": []
    }
  ],
  "СШ ВВС": [
    {
      "id": "perm-location-id",
      "city": "Пермь",
      "region": "Пермский край",
      "required": ["region"]
    },
    {
      "id": "crimea-location-id",
      "city": "Симферополь",
      "region": "Республика Крым",
      "required": ["region"]
    }
  ]
}
```

Endpoint принимает optional-параметры:

```text
GET /admin/locations/aliases/?region_id=<region-uuid>&city_id=<city-uuid>
```

Если оба параметра отсутствуют, возвращается полный справочник. Если передан
хотя бы один параметр, для каждого объекта проверяются только поля из
`required`:

- `region` требует переданный и совпадающий `region_id`;
- `city` требует переданный и совпадающий `city_id`;
- объект с пустым `required` не фильтруется;
- если обязательный параметр отсутствует или не совпадает, объект пропускается;
- если для alias не осталось объектов, ключ alias не возвращается.

Точное разрешение неоднозначного alias выполняется с ID региона:

```text
GET /admin/locations/aliases/resolve?alias=СШ ВВС&region_id=<region-uuid>
```

Если `region_id` не передан, backend возвращает
`3019 LOCATION_REGION_REQUIRED`. Если alias однозначный, параметр региона
необязателен.

`POST /admin/locations/aliases/` разрешает одинаковый alias у разных объектов
только при выполнении обоих условий:

- регионы объектов различаются;
- у существующего и нового объекта `required` содержит `region`.

Во всех остальных случаях возвращается `3021 LOCATION_ALIAS_CONFLICT`.

Если объект уже существует и требуется только дополнить его aliases,
используется отдельный idempotent endpoint:

```http
POST /admin/locations/aliases/{location_id}/aliases/
```

```json
{
  "aliases": ["новое исходное название"]
}
```

## Миграция существующих атлетов

Для неоднозначного alias скрипт `migrate_athlete_locations.py` пытается выбрать
объект по точному нормализованному совпадению `athletes.city`. Если город не
позволяет выбрать ровно один объект, атлет не связывается и попадает в
выгрузку с причиной `alias requires location context` и списком кандидатов.
